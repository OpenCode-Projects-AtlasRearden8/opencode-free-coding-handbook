Welcome — Read Me First

Who this book is for

This book is for anyone who wants to use an AI coding assistant without spending money, without already being a professional programmer, and without feeling talked down to.

Maybe you have an idea for a website, a tool for your small business, a script that saves you an hour a week, or just plain curiosity about how "AI coding" actually works. Maybe you have tried a chatbot in a browser and thought: this is great at explaining, but I want it to actually build things. This book will show you how to do that, for free, using a tool called OpenCode.

You do not need a computer science degree. You do not need to buy anything. Everything in this book can be done with a regular computer, a normal internet connection, and free accounts (or no accounts at all, if you go the local route). Wherever something can go wrong, we will tell you how to notice it and how to fix it.

One promise before we start: we will never assume you already know the thing we are explaining. Every term gets explained the first time it shows up. Every command is written out in full so you can copy it exactly. And if a step feels risky, we will say so — and show you how to make it safe first.

What you will learn

By the end of this book, you will be able to:

  1. Install OpenCode — a free, open-source AI coding agent that runs right in your terminal — on Windows, macOS, or Linux.
  2. Pick a free model and connect it, choosing between cloud providers with free tiers, subscriptions you might already have, and models that run entirely on your own computer.
  3. Set up guardrails so the AI can help you without overstepping — this is the permissions and safety part, and it matters more than most beginners realize.
  4. Write prompts that actually produce good work, instead of vague requests that produce vague results.
  5. Use Git — the industry-standard version control system — as your safety net, so no AI mistake can ever destroy your work.
  6. Review AI changes like an editor, not a spectator, so you stay in charge of your own project.
  7. Understand the limits of free tiers — what you get, what you don't, and how to work around it.
  8. Fix problems yourself using a systematic troubleshooting chapter, because things will occasionally break, and that is normal.

How to read this book

You have two ways to read this:

  • As a book, chapter by chapter. Each chapter builds on the previous ones. If you are brand new to all of this, reading in order is worth it. The appendices at the end are checklists you will come back to again and again.
  • As a reference. Later, when you just need the troubleshooting table or the pre-commit checklist, jump straight to those chapters. They are written to stand on their own.

The one rule of this book

If you remember nothing else, remember this:

Never let the AI be the only person who understands your project.

Free models are good — genuinely good — and OpenCode makes them pleasant to use. But you are the boss here. The AI proposes; you review, you decide, you commit. That single habit is what separates "the AI helped me build something I'm proud of" from "I have no idea what this folder even does anymore." Everything else in this book supports that habit.

About the fine print

Prices, rate limits, model names, and menu options change constantly in the AI world. This book describes how things work as of late 2026, and the techniques here are durable — but the specific numbers (how many requests per day, how big a context window is) will drift. Whenever this book gives a specific limit, treat it as "a typical example, check the provider's current page for today's number." We will remind you of this in the chapters where it matters.

Chapter 1 — What Is OpenCode?

From chatbot to coworkers

You have probably used an AI chatbot in a browser. You type a question, it answers, you copy what you like. That is a conversation.

OpenCode is different. It is an AI coding agent: instead of just talking about your code, it can actually work on it — reading your files, writing changes, running commands in your terminal, and reporting back. The difference is the difference between asking a friend "how do I change a tire?" and handing your keys to a mechanic who does it while you watch.

Here is what an agent can do that a plain chatbot cannot:

Ability Browser chatbot OpenCode (an agent)
Explain code Yes Yes
Read the files in your project Only if you paste them Yes — it can open and read files itself
Edit files directly No Yes, with your permission
Run commands (tests, builds, Git) No Yes, with your permission
Work across many files at once Painfully, via copy-paste Yes — that is its whole job
Remember your project's style No Yes — via an AGENTS.md file it writes for your project

That last row deserves a quick explanation. When you first run OpenCode in a project, you type /init. OpenCode looks around your project, figures out what it is (a blog? a data-cleaning script? a shop?), and writes an AGENTS.md file — think of it as a welcome note to the AI, describing the project layout, the conventions, and the commands that build and test it. From then on, every session starts with OpenCode already knowing the house rules.

What OpenCode actually is

A few facts, so you know what you are getting into:

  • Open source. The code is public; anyone can inspect it. You are trusting software you can read.
  • Runs in your terminal. The main interface is a friendly text-based app (called a TUI — a text user interface). There is also a desktop app and an IDE extension, but this book focuses on the terminal, because it is the most reliable path and teaches you the most.
  • Model-agnostic. OpenCode does not lock you to one company. It supports 75+ providers — big labs, small labs, and your own computer. That is exactly why a book about free AI coding is possible: you can point OpenCode at whatever is free today.
  • Permission-aware. By default it asks before editing files and before running commands. Chapter 4 turns this dial up or down.

The mental model: a junior developer on your team

Beginners often swing between two extremes: treating the AI like a magic oracle, or treating it like a hostile autocomplete. Neither is useful.

The model that works is this: you have hired a junior developer who is extremely fast, extremely tireless, extremely confident — and who does not know your project yet.

What follows from that little story:

  1. You have to give real instructions. "Make it better" is not spec. "Add a search box to the top of the notes page that filters by title, and show 'no results' when nothing matches" is.
  2. You have to review the work. Fast and confident means fast and confident mistakes. Not malicious ones — just ordinary misunderstandings. Your review is the quality control. Chapter 7 gives you the routine.
  3. You should protect the project. A careful senior developer never lets someone push straight to the live product with no review and no undo. Chapter 6 teaches you Git, which is exactly that protection.
  4. You can lean on it for the boring parts. Explaining unfamiliar code, writing repetitive boilerplate, renaming things everywhere, drafting tests — this is where agents shine, and where they free you to think.

If you internalize the junior-developer model, everything else in this book will feel obvious rather than fussy.

The five-step working loop

Almost everything you do with OpenCode follows the same small loop. Learn it once; use it forever:

  1. Ask. Describe what you want, with context. (Chapter 5.)
  2. Plan. For anything bigger than a small tweak, press Tab to switch OpenCode into Plan mode. In Plan mode the AI is forbidden from changing files — it can only propose an approach. You read the plan, correct it, and iterate until it matches what you actually wanted.
  3. Build. Press Tab again to return to Build mode and say "go ahead." The AI edits files, runs commands, and narrates what it did.
  4. Review. Look at what changed (git diff, Chapter 7), ask follow-up questions, and test the result.
  5. Undo or proceed. Happy? Commit your work with Git. Unhappy? Type /undo to back out the changes and try again with a better prompt. OpenCode keeps a history, so you can also /redo if you change your mind — and /undo more than once to walk back further.

Why Plan mode matters. Beginners pay for AI mistakes in churn: "no, not like that — undo — try again." Plans cost seconds; wrong builds cost minutes and leave a mess. The pros you watch in AI-coding videos are mostly just people who insist on good plans.

A tiny tour of the terminology

You will meet these words constantly. Here is the whole cheat sheet in one table — bookmark this page.

Term Plain meaning
Model The AI "brain" — e.g., Qwen 3 Coder, GLM, GPT, Claude. Different models differ hugely at coding tasks.
Provider The company or service that serves a model — OpenAI, Anthropic, Groq, Google, your own machine. Usually you need an account or a programme installed.
API key A long password-like string that proves to a provider that you are you. Keep it secret; never paste it into code you share.
Token The unit of AI text — about ¾ of a word. Providers bill and limit by tokens. Your prompt uses input tokens; the answer uses output tokens.
Context window How much text (your files + conversation) the model can consider at once, measured in tokens. Too-small context = the AI "forgets" things you said.
Free tier A no-cost usage level offered by a provider, usually with daily/monthly limits.
TUI Text user interface — OpenCode's terminal app.
Tool An ability the agent can use: read a file, edit a file, run a shell command, search the web. Each tool can have its own permission rule.
Permission Your rulebook: allow, ask, or deny for each tool. Chapter 4.
Agent mode Build mode vs Plan mode — whether the AI may change things or only propose.
AGENTS.md The project guidebook file that OpenCode reads at startup; /init creates it.
Repository (repo) A folder tracked by Git, so changes are recorded and reversible. Chapter 6.
Diff The line-by-line "what changed" view. How you review AI work.

What OpenCode is not

To keep expectations calibrated:

  • It is not a one-click app builder. It will not guess your business away from you. It needs your decisions, clearly stated. (Chapter 5 fixes that.)
  • It is not infallible. Models sometimes misread intent, invent a function that does not exist, or quietly break a part of your project you did not mention. This is normal, expected, and fully recoverable with the loop above — especially if you have Git.
  • It is not free of judgment. Even with a free model, you are responsible for what it produces and what you ship. Reviewing is not optional bureaucracy; it is the job.

Your first look ahead

In Chapter 2, you will install OpenCode in about ten minutes using one command, open it in a practice folder, and take it for a spin. Then Chapter 3 gets you a capable model without paying anyone anything.

If you ever feel lost in the jargon, come back to the table above. Every beginner is confused by this vocabulary for roughly a week; after that it is simply how you talk.

Chapter 2 — Installing OpenCode

Installation sounds scary if you have never done "developer stuff" before. Good news: it is usually one command, and this chapter shows every option with full copy-paste instructions. Ten minutes from now you will have the tool running.

Step 0: Get a decent terminal first

OpenCode lives in the terminal, so you want a terminal that renders it well. If you are on Windows, the single most important advice in this chapter is: use WSL (Windows Subsystem for Linux). Windows' classic console (cmd.exe) struggles with modern text interfaces. WSL gives you a real Linux environment inside Windows, and OpenCode's own documentation recommends it.

Platform Recommended terminal Notes
Windows WSL (with Windows Terminal as the window) Full compatibility; skips most rendering problems. See Microsoft's "Install WSL" guide, then continue this chapter inside WSL.
Windows (no WSL) Windows Terminal Workable via Chocolatey/Scoop/npm, but expect occasional display quirks.
macOS iTerm2, Ghostty, Kitty, WezTerm, or plain Terminal.app All fine; Ghostty and Kitty are OpenCode's favourite picks.
Linux Ghostty, Kitty, Alacritty, WezTerm Nearly any modern emulator works. Very old ones (or plain xterm) can be flaky.

Installing WSL (once, in PowerShell as Administrator):

wsl --install

Then restart your machine and open the new "Ubuntu" app. Everything below happens in that window, or in Terminal.app/Ghostty on Mac and Linux.

Step 1: Install OpenCode

Pick one method from the table — the first one that matches you. All methods produce the same opencode command.

Your situation Command Where to run it
Linux, macOS, or WSL (easiest) curl one-liner — see just below the table Terminal
You already use Node.js npm install -g opencode-ai Terminal
macOS/Linux with Homebrew brew install anomalyco/tap/opencode Terminal
Arch Linux sudo pacman -S opencode (stable) or paru -S opencode-bin (newest) Terminal
Windows without WSL choco install opencode or scoop install opencode or npm install -g opencode-ai PowerShell
You prefer containers docker run -it --rm ghcr.io/anomalyco/opencode Anywhere Docker runs

Note the | in the curl line below is a real pipe character. Copy it exactly as printed:

curl -fsSL https://opencode.ai/install | bash

Verifying the install

Whatever method you chose, check it worked:

opencode --version

You should see a version number print and the shell come back. If instead you see command not found, your shell does not yet know where opencode lives. Two usual causes:

  1. You just installed it and the shell has a stale list of commands. Close the terminal window completely, open a fresh one, and try again. This fixes it surprisingly often.
  2. The install directory is not on your PATH (the list of folders your shell searches). The npm method is the classic case — try npx opencode as a stopgap, or find the folder npm used (npm config get prefix) and read Troubleshooting (Chapter 9) for the PATH fix.

Keeping it updated

AI tooling moves quickly; update every few weeks:

opencode upgrade        # if your version supports it

or simply re-run the install command for your method — installers happily overwrite an older copy. Check what you have with opencode --version.

Uninstalling (for completeness)

Method Uninstall command

Homebrew brew uninstall opencode
Arch sudo pacman -R opencode
Chocolatey choco uninstall opencode

Step 2: First launch

Now for your first ten wins. Work through this checklist in order — do not skip the practice folder; it keeps the mess far from anything important.

Your first-session checklist:

  • ☐ Have the version confirmed (opencode --version works)
  • ☐ Create a playground, e.g. mkdir ~/opencode-playground && cd ~/opencode-playground
  • ☐ Start the program: opencode
  • ☐ See the chat interface
  • ☐ Exit safely and re-launch it once, so the start/stop cycle is familiar

Type opencode and press Enter:

cd ~/opencode-playground
opencode

You will drop into the TUI: a chat area, a prompt at the bottom, and a help line. The basics:

  • Type a message and press Enter to send it.
  • Ctrl+C twice, or type /exit to leave.
  • /help lists every special command.

Commands that start with / go to OpenCode itself, not to the AI — think of them as the program's menu. You will use these five constantly:

Command What it does
/help List all commands and key binds
/connect Attach a provider/model (Chapter 3 does this together with you)
/models Pick or switch the model you are using
/init Have OpenCode analyse the current folder and write AGENTS.md
/undo, /redo Back out or re-apply the last set of changes

A few keys worth knowing early:

  • Tab toggles Plan ↔ Build mode (bottom-right shows which you are in).
  • @ while typing lets you fuzzy-search and reference files in this project — the single most useful beginner key.
  • Drag an image into the window to attach a screenshot for the AI to look at.

If the display looks scrambled (misaligned lines, colours everywhere), your terminal is the culprit, not you — return to the table at the top and try Ghostty, WezTerm, or Kitty. Chapter 9 has more fixes.

Step 3: Meet AGENTS.md (your project's welcome note)

While still in the playground, run:

/init

OpenCode will look around, and in an empty folder it has little to say — that is fine and quick. In a real project it writes an AGENTS.md file in the project root describing structure, style, and how to run things. Two habits to build now:

  1. Re-run /init after big structural changes so the welcome note stays accurate.
  2. Commit AGENTS.md to Git (Chapter 6). It is part of your project, and committing it means the AI (and collaborators) always have the same briefing.

Later, you can hand-edit AGENTS.md to add house rules, e.g. "always answer in plain English" or "never edit files in ./archive". OpenCode reads it as instructions every session.

Step 4: Point OpenCode at a model

Right now OpenCode is a car with no engine: it has no model to think with. The /connect command walks you through attaching one — another provider, a subscription you already own, or a model running on your own machine. That is the entire subject of Chapter 3, which is where we go next.

Where your credentials live (so you stop worrying)

When you paste an API key during /connect, OpenCode stores it on your machine — in ~/.local/share/opencode/auth.json on Linux/macOS/WSL — not inside your project folder. Three consequences:

  • You can commit your project to git without leaking keys (but check anyway — Chapter 6 shows how).
  • Anyone with access to your user account can read that file, like any password cache.
  • If you suspect it leaked, revoke the key at the provider's website, not by deleting the file — then re-connect.

Common first-run feelings (and why they are fine)

  • "The terminal feels alien." It is a muscle, not a talent. You will use about six commands for 90% of your work, and this book prints every one.
  • "I'm afraid I'll break something." With Git (Chapter 6) you gain a time machine. Until then, stay in your playground folder.
  • "The AI's answers feel vague." Almost always the prompt, not the tool — and Chapter 5 is entirely about prompts.

Checkbox recap of this chapter

  • ☐ Chose and opened a good terminal (WSL on Windows)
  • ☐ Installed OpenCode with one command
  • ☐ opencode --version prints a version
  • ☐ Launched and exited the TUI
  • ☐ Ran /init in a practice folder
  • ☐ Know where ~/.local/share/opencode/auth.json lives

When every box is ticked, you are ready to give your agent a brain — for free.

Chapter 3 — Picking Free Models

OpenCode is the tool; the model is the engine. This chapter gets you an engine without spending money, and explains the honest trade-offs you are making.

What "free" really means

"Free" in this world comes in four flavours. You will meet all of them, so learn to tell them apart:

Flavour What it is Catch
Free tier (cloud) A hosted model you can call from OpenCode with a signup, limited by requests per day/month or tokens Limits, slower queues, sometimes weaker models served
Subscription you already own A ChatGPT Plus, GitHub Copilot, or GitLab plan you already pay for elsewhere — OpenCode can use it for coding with zero setup Not "free," but no new money; subject to that plan's caps
Free credits / promotional Start-up providers giving new accounts a helping stack of tokens Runs out; better as a taste than a plan
Local models Open-weights models running on your computer via Ollama, LM Studio, or llama.cpp No limits ever, but your hardware and patience are the budget

The overriding truth, stated kindly: the free world is real and good. Free and open-weights coding models — the Qwen-Coder family, GLM series, DeepSeek-Coder variants, Llama, and friends — are routinely capable enough to build small projects, clean data, write scripts, and maintain a website. You are not choosing between "free" and "useful." You are choosing speed, patience, and privacy trade-offs, which the table below makes concrete.

Trade-off axis Cloud free tier Local model
Cost 0 (with caps) 0 (with your electricity)
Speed Usually fast, sometimes throttled Depends on your machine
Privacy Your code travels to the provider's servers Code never leaves your machine
Quality ceiling Usually higher Smaller models, smaller context
Setup Account + API key Install a program + download model files
Limits Daily/monthly caps None — run it till your fan gives up

The two setup recipes you'll actually need

Recipe A: GitHub Copilot (the smoothest cloud start)

  1. Make sure you have a GitHub account (free to create).
  2. In OpenCode, run /connect, search for and choose GitHub Copilot.
  3. OpenCode shows a short code and the address github.com/login/device. Open that page in a browser, enter the code, and approve.
  4. Back in OpenCode, run /models and pick a model.

Notes worth knowing:

  • Some models require paid Copilot plans (Pro+); the free plan's models still work fine for learning.
  • If you later see "model requires a higher plan" errors, pick a different model from /models — nobody is charging you here, the menu is just saying that one's not in your tier.

Recipe B: Ollama (the local, unlimited start)

Ollama runs models on your own computer. Nothing leaves your machine — which matters for medical-adjacent work, small business records, or anything private.

  1. Install Ollama from ollama.com (Windows and macOS installers; Linux a one-line script).
  2. Pull a coding model from your terminal, e.g.:

bash ollama pull qwen3-coder:7b

(Model names and size tags change — browse the library at ollama.com/library and pick a coder model that fits your hardware. As a rule of thumb: about 8 GB of RAM will run a 7–8B model; 16 GB or a modest GPU comfortably runs the bigger useful ones.) 3. Tell OpenCode about the provider by adding this to ~/.config/opencode/opencode.json (create the file if needed):

json { "$schema": "https://opencode.ai/config.json", "provider": { "ollama": { "npm": "@ai-sdk/openai-compatible", "name": "Ollama (local)", "options": { "baseURL": "http://localhost:11434/v1" }, "models": { "qwen3-coder:7b": { "name": "Qwen3-Coder 7B (local)" } } } } }

  1. Restart OpenCode, run /models, and you will see your local model listed.

Two local-model tips that save hours:

  • Increase the context size: if tool calls misbehave or the model "forgets," raise Ollama's num_ctx (start around 16k–32k). Small default contexts are the number-one cause of flaky local behaviour.
  • Check the model is running: ollama ps shows what is loaded; ollama run qwen3-coder:7b lets you chat with it directly to confirm it works outside OpenCode.

The real selection criteria (beyond "is it free")

Tick these five boxes whenever you evaluate a free model:

  • ☐ Does it support tool calls? OpenCode is an agent — it needs models that can call tools (read/edit files, run commands). Non-tool-calling models can chat but will fail at agentic jobs. Coder-focused models (Qwen-Coder, DeepSeek-Coder, big GLM variants, frontier models) are the safe picks.
  • ☐ Is the context window big enough? Your whole project's key files and the conversation must fit. If the model has ~8k tokens of context, ambitious tasks will break in confusing ways. Prefer comfortable contexts (128k is common this decade).
  • ☐ What are the actual rate limits today? Check the provider's own pricing/limits page — not this book — before planning a work day around it.
  • ☐ What is the privacy story? Cloud free tiers often may use your data for training. If the content is sensitive (client data, health information, business records), use a paid key or a local model. Say it plainly: do not paste anything you would not put on a postcard through a public free tier.
  • ☐ Is there a "plan" model and a "build" model? A common free-tier strategy: use a strong model for planning (rare, precious requests) and a faster one for execution (plentiful requests). Chapter 8 builds on this.

A simple starting recommendation

If you want one default answer rather than a research project:

  • Comfortable and social: GitHub Copilot's free plan (Recipe A) — fewest moving parts if you already have GitHub.
  • Private and unlimited: a Qwen3-Coder-class local model via Ollama (Recipe B) — the "free forever" path, gated by your hardware.
  • Experimentation budget: OpenRouter's :free suffix models or Groq/Cerebras/NVIDIA free tiers — great for taste-testing models before committing to one.

And remember: switching models is one command (/models), so this decision is cheap to revisit. You are not marrying a model; you are hiring per task.

  • ☐ You can name the four flavours of "free"
  • ☐ Connected at least one cloud model via /connect, or
  • ☐ Set up Ollama with a local coding model in opencode.json
  • ☐ /models shows your choice and you have chatted with it once
  • ☐ You checked the provider's current limits page (today's numbers, not a book's)
  • ☐ You know the privacy posture of whichever model you picked

Chapter 4 — Permissions and Safety

Here is the sentence that makes this chapter matter: an agent that can edit files and run commands is powerful, and power without guardrails is how beginners get hurt. OpenCode ships with sensible guardrails. This chapter shows you how they work, how to tune them, and how to develop habits that make AI coding safe even on a free model.

The permission dial: allow, ask, deny

OpenCode uses a permission config to decide, for every action it wants to take, one of three answers:

Setting Meaning Feels like
"allow" Runs without asking you Trust-but-log
"ask" Prompts you; you decide each time Traffic light on yellow
"deny" Blocks the action entirely Hard fence

Every tool can get its own setting. The main keys, straight from OpenCode's design:

Permission key Controls
read Reading files (rule matches the file path). .env files are denied by default — see below.
edit All file changes (edit, write, patch)
shell Terminal commands (matches the command text, e.g. git status --porcelain)
glob / grep File searches
webfetch / websearch Fetching URLs / searching the web
task Spawned subagents
skill Loaded skills
external_directory Touching files outside the folder you started OpenCode in (asks by default)
doom_loop Detects the AI repeating the identical failing tool call three times (asks by default)

Where the rules live, and how they match

Put rules in your OpenCode config — globally at ~/.config/opencode/opencode.json, or per-project in opencode.json at the project root. The simplest global stance:

{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "*": "ask",
    "edit": "allow"
  }
}

This says: let the AI edit files freely (you will review via Git anyway — Chapter 6), but ask before every terminal command, web fetch, and everything else. That is a wonderful beginner posture. It is a little more clicky, but each prompt is a free safety lesson about what the AI is currently doing.

Rules match with patterns, and the last matching rule wins. A common and sensible pattern: allow safe read-only commands, ask about the world, deny the genuinely dangerous:

{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "shell": {
      "*": "ask",
      "git *": "allow",
      "npm *": "allow",
      "grep *": "allow",
      "rm *": "deny"
    }
  }
}

Notes on pattern matching, because everyone trips here once:

  • * matches anything; ? matches exactly one character.
  • "grep *" allows grep thing file.txt. Bare "grep" would not cover grep with arguments — patterns must include the wildcard to cover arguments.
  • Last rule wins, so specificity goes after the catch-all. In the example above, rm * comes after "*" on purpose.
  • Also useful: "git push *": "deny" in any config where you never want the AI to publish anything. This book's default stance is exactly that: the AI reads, writes, and commits locally; pushing to the internet stays your job.

You can also restrict where OpenCode may even look. Paths outside the start folder are gated by external_directory (asks by default). Keep it that way unless you have a reason.

What "ask" looks like, and the three answers

When OpenCode prompts you, you pick from:

  • once — approve this single request;
  • always — approve this category of requests for the rest of the session (e.g. all git status* commands);
  • reject — no.

Beginner guidance: read the prompt. It shows exactly what will run. If a shell command surprises you — press reject, then ask the AI why it wanted to run that. Surprises are information. If nothing surprises you any more, that is your cue that always is safe for that category.

Auto mode: speed with a fence

opencode --auto auto-approves everything that would normally ask — except rules explicitly set to deny, which still bite. It is great for long, well-understood tasks on a safe project. It is not for your first week. If you use it, keep at least these denies in place:

  • ☐ rm * (or at minimum any pattern touching files you care about)
  • ☐ git push * (publishing stays manual)
  • ☐ webfetch / websearch if you want the AI browsing only when you say so
  • ☐ .env reads (the default denies them; keep it that way)

Secrets: the non-negotiables

Some rules in this book are habits; these are laws:

  1. Never put API keys in files inside your project. Keys belong in OpenCode's auth store (~/.local/share/opencode/auth.json) or environment variables — nowhere else, not even "temporarily."
  2. Never let .env contents into a conversation. OpenCode denies reading .env by default on purpose — leave it that way. If the AI truly needs a value from .env, set it as an environment variable yourself or tell the AI which value in words, without pasting the secret.
  3. Never commit secrets to Git. Chapter 6's .gitignore protects you; the reviewing chapter (7) has a pre-commit secret check.
  4. Rotate, don't panic. If a key leaks (committed, pasted, shared), go to the provider's website and revoke/rotate it. That takes two minutes and neutralizes the leak.
  5. Mind AI-supplied links. Free models occasionally hallucinate plausible-looking URLs. Never log in "via a link the AI gave you" — navigate to the provider's site yourself.

Privacy: where does your code actually go?

With a cloud model, your prompts — meaning your code and file contents — travel to that provider's servers. Facts to internalize:

  • Local models (Ollama, LM Studio, llama.cpp) keep everything on your machine. Strongest option for sensitive material.
  • Free cloud tiers often train on your data. If the provider's free tier says it may use data to improve models, that text usually means exactly what it appears to mean.
  • Sessions may be shareable. Some OpenCode versions can publish a share-link of a session. If such a feature is present, treat it like publishing pages on the internet — a fine way to show off a demo project, a terrible way to "ask friends about" anything private.
  • As a nurse-turned-author, our founder's rule is worth borrowing: treat patient, client, or customer details as radioactive in any AI context unless the tooling is explicitly designed and contracted for it. This book is about tools and learning; it is never a place to paste real case data.

Your first-signin safety checklist

Do these five minutes of tuning once, then relax:

  • ☐ Set "*": "ask" for shell (commands get prompts)
  • ☐ Add "rm *": "deny" to shell rules
  • ☐ Decide on "git push *": deny while you learn, ask later
  • ☐ Leave read rules at default so .env stays denied
  • ☐ Leave external_directory at ask
  • ☐ Check your model choice's privacy posture (Chapter 3)
  • ☐ Confirm keys live in auth.json or env vars, not project files
  • ☐ Turn off auto-approvals (--auto unused) until Git is in your routine

A gentle word about what safety is for

Safety rails are not distrust of you. They exist because this is a new way of working: software now proposes changes to your disk, your terminal, and your network, and the human reviewing it is learning to review. Every prompt you approve in your first weeks is a tiny education in what agents do. By the time auto mode truly suits you, you will know why — because you will have read a hundred of those prompts. That earned confidence is the whole game.

Chapter 5 — Writing Good Task Prompts

Bad prompts are the single biggest cause of "the AI is useless" experiences — and the fix costs nothing. This chapter gives you a formula, worked examples, and the little OpenCode mechanics (@, images, Plan mode) that turn decent prompts into great ones.

The four-part prompt formula

Every good task prompt contains four ingredients. You do not need perfect style; you need all four present:

  1. Goal — what you want to be true when the work is done.
  2. Context — where the work happens (files, folders, examples of similar things).
  3. Constraints — boundaries: what not to touch, style rules, keep it simple.
  4. Definition of done — how you will check the result (a page opens, a test passes, a file is created).

A friendly way to remind yourself: goal, where, guardrails, and how I'll know.

Bad and good, side by side

The jump from bad to good is smaller than you think — it is just the four parts, said out loud:

Vague prompt Good prompt
"Fix my website." "Goal: the /contact page's form should send submissions to a local text file and show a success message. Context: it lives in site/contact.html and js/contact.js. Constraints: don't change other pages; keep styling as-is. Done: submitting the form produces a line in submissions.txt and a visible success note."
"Make the data cleaner." "Goal: remove duplicate rows in data/patients.csv where ID matches, keeping the earliest VisitDate. Context: it's a CSV with a header row; dates are YYYY-MM-DD. Constraints: don't reorder rows otherwise; warn me how many duplicates you removed. Done: the output file has a count of removed rows and opens without errors."
"Add tests." "Goal: add tests for the slugify() function in src/text.js. Context: test pattern for this project is tests/*.test.js; see tests/none-yet. Constraints: use the project's existing test style; no new dependencies. Done: npm test passes and covers empty strings, uppercase, and repeated dashes."
"Can it have a dark mode?" "Goal: add a dark/light toggle to the reader page. Context: colours live in style.css; the toggle button can sit in the top-left of reader.html. Constraints: store the choice in localStorage; don't add frameworks. Done: toggling survives a page refresh."

Notice what the good column is not: jargon-heavy, clever, or long. It is just explicit about the four parts. Beginners routinely under-specify the definition of done, which is the part the AI also uses to check itself before handing you work.

Work across the table from your junior developer

Chapter 1's mental model pays off here. You would not say "make onboarding better" to a new hire and walk away. You would hand them a ticket. Write prompts like tickets:

  • One task per prompt. Sequential, small asks beat a single giant wish. Small tasks also fit small context windows (relevant for free models, see Chapter 8) and produce reviewable diffs (Chapter 7).
  • Point at concrete things. Use @ while typing to reference real files (@src/app.js); OpenCode pulls the file into the AI's attention. Reference by-with example: "handle it like the other routes do in @packages/functions/src/notes.ts".
  • Invite questions. "Before you start, ask me anything unclear" is a magic sentence. It converts silent wrong guesses into a short conversation you can afford.
  • Give constraints you care about but wouldn't think to say: "plain JavaScript, no frameworks"; "don't reformat files I didn't mention"; "comments only where code isn't obvious"; "never edit files under archive/".
  • Let it propose, then choose. For anything design-flavoured, ask for three options with trade-offs before building any. Choosing between sketches is easier than undoing a building.

The Plan → Build drill

This rides on Chapter 1's loop but deserves its own drill, because it is the quality lever:

  1. Press Tab into Plan mode.
  2. Write the four-part prompt.
  3. Read the plan as if grading someone's work. Fix: missing steps, wrong files touched, scope creep, anything it "assumed" that you did not say.
  4. Iterate the plan with short replies ("step 2 should use the existing helper in @utils/date.js, not a new one").
  5. When the plan matches your intent, Tab back to Build mode and say: "Approved — go ahead with exactly this plan."

Cost of all that: two minutes. Cost of not doing it: a bad half-hour of undoing. On free tiers this is also simply the cheapest way to spend tokens.

A worked example (start to finish)

Task: you want to build a soft-delete flow for notes — the same example shape OpenCode's own documentation demonstrates, and a very common real-world need.

In Plan mode:

Goal: when a user deletes a note, we flag it as deleted in the database instead of deleting it. Then add a "Recently deleted" screen where a note can be undeleted or permanently removed. Context: notes live in src/notes/; the database layer is src/db.js; see how the existing list view in src/notes/list.js is structured and match it. Constraints: no new dependencies; keep the UI style consistent; don't touch anything outside src/notes/ and src/db.js. Done: deleting a note hides it from the main list, it appears under Recently deleted, undelete puts it back, permanent delete is possible but asks for confirmation.

Iterate the plan if needed. Then, in Build mode: "Approved — implement this plan."

After it builds: review (Chapter 7), run the app, and commit. A real feature, built by an AI, understood by you.

Small-mechanic chapter: things OpenCode gives you for free in prompts

Mechanic Use
@file references Pull specific files into context ("see how @notes.ts handles auth")
Drag-and-drop images Screenshots of the design you want matched; error popups for debugging
Plan mode (Tab) Force a review-first workflow
/undo, /redo Cheap iteration: change the prompt, not the mess
/init + edits to AGENTS.md Put standing preferences in AGENTS.md ("in @AGENTS.md: always answer in plain English") so you stop repeating them
Follow-up "why did you…?" The best review engine is the chat itself — make the AI explain its own changes

Prompt anti-patterns to retire

Retire these habits now, with love:

Anti-pattern Why it fails Replacement
"Make it good/professional/modern" Untestable; guarantees generic output Concrete description of the visible result
Ten tasks in one prompt First three get done, rest forgotten, context fills One ticket per prompt, sequenced
"You're an expert, just do it" Confidence theatre; moves nothing Provide the context and done-definition
No mention of files AI wanders the project guessing @ references to real files
"Rewrite everything from scratch" Throws away unreviewed value Ask for a targeted change or an new module
Silence when unhappy Rolls with the bad version Say exactly what's wrong; re-prompt or /undo

Checklist: before you press Enter

Glance down this list when you finish typing any prompt:

  • ☐ The goal is a result, not a mood
  • ☐ Context: real files are referenced (with @ where possible)
  • ☐ Constraints that matter are stated (scope, style, no-new-deps)
  • ☐ Definition of done is checkable by you, not just the AI
  • ☐ It is one task (or an explicitly-sequenced plan)
  • ☐ In Plan mode, if the change is bigger than a tweak
  • ☐ Long-term preferences live in AGENTS.md, not in every prompt

That's the craft. Next chapter: the safety net beneath all of this.

Chapter 6 — Git Basics (Your Safety Net)

Git is the one tool in this book that has nothing directly to do with AI — and is the reason AI coding is safe for beginners. Git records snapshots of your project, called commits, so that any mistake — yours or the AI's — can be reversed with one command. Everything else in this book quietly assumes you know this chapter.

The idea in one paragraph

Imagine you save a copy of a document before every edit, forever, into a numbered archive that takes no space and never gets mislabelled. That is Git. A repository ("repo") is a project folder that Git archives. A commit is one archived snapshot with a label you wrote. A diff is the difference between two snapshots. That vocabulary plus six commands is 95% of what beginners need.

Setup once, per computer

Tell Git who you are (this goes into the archive labels of commits you make):

git config --global user.name "Your Name"
git config --global user.email "you@example.com"

The email does not need to be real for local work, but using your real one matters later if you publish to GitHub, since GitHub links commits to accounts by email. Nothing in this book requires an online service; Git is fully local.

The six commands that matter

Command What it does When you type it
git init Turn this folder into a repo Once, at the start of a project
git status Show what changed and what's staged Constantly; your dashboard
git add -A Stage all current changes for the next snapshot When you like what you see
git commit -m "…" Save a labelled snapshot Every time you reach a good state
git log --oneline List past snapshots short When you want an overview
git diff Show unstaged changes line by line Before staging — your review screen

And for emergencies (learn these the day something breaks):

Command What it does
git restore <file> Discard unsaved changes to a file — back to last commit
git restore --staged <file> Unstage a file you add-ed by mistake
git checkout <hash> Travel back in time to look at any old snapshot, read-only
git branch <name> / git checkout -b <name> Create a parallel history (see below)
git merge <name> Blend a branch's work back into the main line

Nothing here touches the internet. This book keeps you local-first: GitHub is a good future step, but you do not need accounts or remotes to be protected.

.gitignore: files Git should never touch

Some files should never enter history: caches, build output, and above all secrets. Put a .gitignore file in your project root on day one:

# Never commit these
.env
.env.*
*.pem
*secret*
auth.json

# Usually noise
node_modules/
__pycache__/
.DS_Store

Check that it works:

  • ☐ git status shows no .env (or similar) as untracked after you add .gitignore
  • ☐ node_modules/ (if you use it) is invisible to git status
  • ☐ The .gitignore itself is tracked (it's a project file, and a great one)

Note the difference in defaults you already carry from Chapter 4: OpenCode refuses to read .env by the same logic — secrets stay out of conversations and out of history.

The recommended AI-working rhythm

This is the chapter's gift to your future self: a rhythm that makes AI work trivially reversible.

  1. Start clean. Before asking the AI for anything, git status should say "nothing to commit." If not, commit or discard the old work first — never mix old and new in one review.
  2. Commit before you prompt. A commit right before each AI task is a restore point keyed by task (write it in the message: "before dark mode feature").
  3. Let the AI work. Approve, watch, keep Git untouched.
  4. Review the diff (git diff, Chapter 7 teaches the routine).
  5. Commit the result — or roll back. Good? git add -A && git commit -m "add dark mode toggle". Bad? git restore . and nothing of value was lost — your last commit still stands.

Optionally level up with branches: git checkout -b dark-mode before a bigger feature, explore there, git merge dark-mode when satisfied. A branch is a free sandbox that protects the main line; it pairs beautifully with AI experiments.

Writing commit messages that help (including with the AI)

A commit message is a label for your future self. Patterns that cost seconds and pay for weeks:

  • Present tense, imperative-ish, specific: add slugify helper with tests, fix crash on empty photo name, not fixes / stuff / asdf.
  • Why beats what: cap crops at 1200px (eBay requires min 800) is gold six months later; resize images is decorations.
  • One idea per commit: if the message needs the word "and" three times, make two commits.
  • Never commit secrets or junk files: check git diff --staged before any commit if you are unsure what you staged.

What to commit — including AGENTS.md

Short answer: everything that defines the project. Specifically relevant to this book:

File Commit it? Why
Source code (src/, etc.) Yes Obviously
AGENTS.md Yes Your AI briefing travels with the project; per OpenCode's own advice
README, config, test data (fake) Yes Part of the project
.gitignore Yes Protects the future
.env, keys, auth.json Never Secrets
node_modules/, build output No Reproducible from source; huge
Large media you could regenerate Usually not Keeps repo snappy

Your rhythm as a checklist

Print this. It is the operational spine of the whole book:

  • ☐ Repo initialized (git init), user configured
  • ☐ .gitignore in place, secrets excluded
  • ☐ Working tree clean before each AI task
  • ☐ Commit before prompting (snapshot A)
  • ☐ git diff reviewed after the AI's work
  • ☐ Commit after acceptance (snapshot B) or git restore . to roll back
  • ☐ Messages: specific, one idea each, no secrets

With this rhythm, the scariest sentence in AI coding — "I don't know what it changed" — becomes a question with a nine-character answer: git diff. On to reviewing, proper.

Chapter 7 — Reviewing AI Changes

If prompts are how you direct the AI, review is how you keep your project yours. Skipping review is how people end up with folders they no longer understand. This chapter gives you a light, repeatable review routine — light enough that you'll actually do it every time.

The mindset

Treat every AI change like a pull request from a new coworker: competent, fast, occasionally wrong about details, always acting in good faith. You don't read it looking for evil; you read it looking for misunderstandings. Then — and this is the part people forget — you are the one signing the work. "The AI wrote it" is not a defence anywhere in life.

Step 1: See what changed (git diff)

The review always starts in the same place:

git diff          # unsaved changes, line by line
git diff --stat   # just the file list and sizes first

Reading order that works:

  1. --stat first — how many files? Does the scope match the task? (You asked for a dark-mode toggle and it touched 14 files? Ask why before reading anything.)
  2. Then read the diff of each changed file top to bottom. Lines starting with + were added, - removed.
  3. Anything confusing stays confusing until you've asked. "Explain @src/app.js changes from this diff" in OpenCode is legitimate review, not cheating — make the AI teach you its own change.

Scope-of-work check. The most common AI mistake is not bad code; it is more code than you asked for: extra helpers, reformatting of untouched files, "improvements" beside the point. If you see it, say so: "revert everything except the dark-mode toggle changes." Scope discipline is review.

Step 2: Run the thing

Code review that never runs the code is just reading fiction. The checklist:

  • ☐ The program/app runs and does the new thing
  • ☐ The old things still work (the new toggle didn't break list view)
  • ☐ The done-definition from your prompt is met — you wrote one, it's checkable
  • ☐ Error paths: give it bad input, slow network, empty file — does it grumble politely instead of crashing?
  • ☐ If tests exist: they pass (and if none exist and the change is logic, ask the AI to add some — "no new dependencies")

Step 3: Read it like an editor

You are not hunting for perfect style; you are triaging risk. Look for these frequent, findable problems:

Red flag Looks like Triage
Scope creep Files touched that the task didn't involve Ask to revert to task scope
Hard-coded secrets Something that looks like a key/token in the diff Remove & rotate — non-negotiable
Lying logs // this function is unused on a function now used everywhere Ask the AI to recheck comments; stale comments are a classic
Missing error handling Code assuming files exist, networks answer, users don't do weird things Ask: "handle the empty case / offline case / invalid input"
Over-engineering A config system, three abstractions and a factory for one feature "Simplify to the smallest version that meets the done-definition"
Magic behaviour Works but you can't explain why Refuse it. Ask the AI to explain plainly until you can
Copy-paste clones The same function appears in two files "Deduplicate — keep one, referenced from both"
Suspicious URLs Looks-plausible links/pages created wholesale Never trust AI-made links without checking

You will not catch everything at first. You will get dramatically better in a month, mostly through the review prompts in the next section.

Step 4: The review prompts (your unfair advantage)

OpenCode can help you review — and free models are typically better at critical reading than at perfect generation. Use it:

  • "Explain the changes from this last task as if I'm new: what, why, and what could go wrong."
  • "What is the riskiest part of the change you just made? What would you test first?"
  • "Review your own diff like a stern senior dev. List anything you'd be embarrassed about." (Great on good models, comedy on small ones — but both are useful.)
  • "Write three quick test cases for slugify() — normal, empty, weird input." Then make it implement and run them.

Also remember /undo and /redo: OpenCode keeps a history of change-sets, so iterating ("that's 90% right, but the toggle should sit top-left") is cheap. Undo does not replace Git — it replaces re-prompting from scratch.

Step 5: The accept ritual

When satisfied, make the acceptance formal — this doubles as the end of the loop:

git add -A
git commit -m "add dark-mode toggle with saved preference"

If instead you are not satisfied and the AI's second attempt gets worse rather than better:

git restore .     # back to your pre-task snapshot

…and then change the prompt, not the code. Two failed generations is a prompt problem; a fresh-scope task or a Plan-mode pass will usually do better than a third wild attempt.

A note on formatters and standards

If your project uses a formatter (e.g. Prettier, Black), run it after AI changes and review that diff separately. Judging style is a waste of your review attention — the machine can settle style; you settle meaning. OpenCode can also be configured to run formatters automatically (its formatter settings), which is worth doing once your routine is stable.

Review on a budget (free-tier friendly)

Reviewing is one of the cheapest things a free model does well, since it is usually short-input, short-output: diffs, explanations, test suggestions. A frugal pattern that works surprisingly well:

  1. Big, careful Plan with your best/strongest allowed model (rare requests anyway).
  2. Build with whatever model your tier handles comfortably.
  3. Review — cheap, free-friendly — with the same or even a different capable model.
  4. Commit locally. No tokens required for steps 3's Git part at all.

The review checklist (shrink onto a card)

  • ☐ git diff --stat — scope matches the task
  • ☐ Full diff read (or read with AI narration where unclear)
  • ☐ Ran the thing; done-definition met; old features intact
  • ☐ No secrets or weird URLs entered the diff
  • ☐ Self-review prompt: "riskiest part? would you be embarrassed anywhere?"
  • ☐ Formatter run, if one exists
  • ☐ Accepted → commit. Not accepted after two tries → git restore ., new prompt

Review might feel slow as you read this. In practice it is minutes, and it is the exact habit that keeps the AI a tool rather than a hazard. Now, let's look honestly at what free tiers give you — and what they don't.

Chapter 8 — Limits of Free Tiers (and Working Within Them)

Free is a real option, not a broken version of paid. But free has edges, and beginners exhaust good free setups for lack of knowing the edges' shapes. This chapter maps the limits so you can plan around them instead of being surprised by them.

The rules of the free game

Limit Where you feel it What it actually means
Rate limits / quotas "Too many requests" / 429 errors, slowed-down replies A count of requests or tokens per day/month. The commonest free-tier limit.
Reduced served quality Free tier may route you to a smaller/older model at peak Same model name can quietly vary in power
Context window constraints The AI "forgets" files, loses the thread on long chats Everything (conversation + referenced files) must fit in the window
Feature gating Some models or settings simply missing from your plan The provider reserves high tiers; you get the generous floor
Throttled speed Great at 9 AM, slow at 6 PM Shared pools get crowded
Training on your data Privacy posture on free tiers (see Chapter 4) Free often = your texts may train them
No uptime guarantee Occasional errors on heavy days Free tiers fail hardest exactly when everyone else is there too

The most important habit in this chapter: verify today's numbers on the provider's own page. Limits change monthly in this industry. This book teaches shapes and strategies; websites carry today's truth.

Recognizing the symptoms early

Free-tier exhaustion announces itself politely before it ruins your day:

Symptom Likely limit First response
429 / "rate limit" errors Quota exhausted Wait for reset; switch model/provider; finish task later
Replies get shorter or trail off Output caps or mid-session throttling Split the task; finish in a follow-up prompt
"I don't have the file you mentioned" Context window filled Reference fewer files; start a fresh session for new tasks
Increasingly generic answers Small model substituted / context bloat Restart session; compact the ask
Long errors mid-day Provider under load Local model (if set up) or revisit at off-peak

None of these mean you did something wrong. They are the simplest, bleakest weather report for free-tier users, and now you read it fluently.

Strategy 1: Match model to task size

The single most effective habit: spend scarce powerful-model requests where they pay, and not a token more.

Task Spend pattern Why
Writing a Plan for a multi-file feature Strong model, careful prompt The plan steers everything downstream
Executing the approved plan Fast/cheap model Steps are now mechanical
Reviewing a small diff Any model Short in, short out
Explaining unfamiliar code Any model Chat, not creation
Giant refactor across 15 files None, or local big-model Small context models will mangle it
Chatting through concepts Free/cheap Zero-risk usage

Strategy 2: Make AGENTS.md do the remembering

Every token of project context you state in a prompt is a token re-spent forever. Instead, put stable facts in AGENTS.md (see Chapter 2) — structure, conventions, commands — and re-run /init when the project shape changes. Cheap models do much better when the briefing is in the file rather than the chat, and you stop paying to re-describe your project daily.

Strategy 3: Plan offline; build with a lean budget

A pattern that turns an exhausted daily quota into a productive day:

  1. Morning (fresh quota): Plan mode with your best model; revise until perfect; save the plan on paper (literally — copy it into your notes or a PLANS.md file).
  2. Midday (quota running low): Build mode executes the plan; approve prompts; make commits along the way (Chapter 6).
  3. Quota gone: human review of diffs (Chapters 6–7), local Ollama run for questions, or simply stop where the next step is mechanical for tomorrow-you with a fresh quota.

Written plans are portable between models and days — one of the quiet superpowers of Plan-first work.

Strategy 4: Keep a rotation

Because /models switching costs nothing, experienced free-tier users keep two or three paths warm (Chapter 3's menu):

  • Primary cloud free tier (e.g. Copilot free plan or a fast open-weights host like Groq/Cerebras)
  • Local Ollama model for privacy, off-grid work, and when all quotas blink
  • OpenRouter :free models as a wildcard sampler
Situation Rotation move
Primary quota hit Switch to secondary cloud for the rest of the task
Privacy-sensitive content Local model, full stop
Cloud simply errors today Local until it clears; or plan-with-paper (Strategy 3)
Need a big-context reasoning pass Whichever path currently offers the biggest window

Strategy 5: Know what free models are actually bad at

Honest limits of small/free models, so you stop blaming yourself for them:

  • Long, coherent multi-file refactors. They lose the plot; scope decisions wobble. Keep refactors small or make them yourself with AI as navigator.
  • Subtle security reasoning. They can name common vulnerabilities yet still write one. Ask a stronger model (or a second model) to security-review anything that touches auth, files, or user input.
  • Ambiguity. They guess rather than ask. Your four-part prompts (Chapter 5) and "ask me anything unclear" fix most of this.
  • Consistent style across a project. Expect drift; let formatters (Chapter 7) pick up the slack; correct slowly creeping architecture in review.
  • Endless patience inside one session. Context fills; sessions get dumber at the end. Start fresh sessions for new tasks — it is not a memory problem you can fix by trying harder.

When free is genuinely enough

A grounding table, because most beginners over-fear this question:

Project type Free-tier verdict Notes
Learning, practice, toy apps Enormously enough This is free tiers' home turf
A personal website/blog Enough with patience Mostly small tasks, reviewable diffs
Small business tools (checklists, converters, trackers) Enough Keep data local or private; review security-sensitive parts
Automation scripts for you Enough Test with fake data first
Serious app with real user data Possible, not first choice Paid models/local help; security review matters
Anything with other people's personal data Caution first Privacy rules beat savings; local models for dosage— see Chapter 4

The free-tier triage checklist

Keep for days when things feel slow or sticky:

  • ☐ Which limit am I actually hitting (rate limit? context? quality floor?)
  • ☐ Have I restarted the session for a fresh context?
  • ☐ Is today's task actually plan-shaped → save a plan, build leaner
  • ☐ Has AGENTS.md been re-run at /init since the last structural change?
  • ☐ Should this task size go to the local model instead?
  • ☐ Checked the provider's current limits page within the last month?
  • ☐ Am I mid-rotation? (/models is one command — use it)

Free tiers are the reason this book exists: real coding help at real zero dollars. Treat them like a shared community garden — plan your plots, take turns, and it will feed you well.

Chapter 9 — Troubleshooting

Everything breaks sometimes — terminals, keys, models, permissions — and the fix is almost always in the top ten possibilities. This chapter is a giant symptom → cause → fix table plus a few "get unstuck manually" walkthroughs. Keep it open when something misbehaves; skim it on a good day so it's familiar on a bad one.

The universal debugging drills

Before the tables: three habits that solve half of all problems before you look anything up.

  1. Reproduce it exactly. Same command, same folder, same order. Flaky problems are diagnosis-eaters; a stable reproduction is half the diagnosis.
  2. Change one thing at a time. New terminal? Or new model? Not both. One variable, then test.
  3. Read the actual error. Out loud, like it matters. Most are surprisingly plain: command not found, 401, permission denied. Match them below.

Part A: OpenCode itself

Symptom Likely cause Fix
opencode: command not found Shell PATH doesn't include install dir, or stale shell Open a fresh terminal; if persists, find the install dir (npm config get prefix for npm) and add its bin to PATH (Ch. 2)
TUI renders scrambled / colours wrong Weak terminal emulator Switch to Ghostty, WezTerm, Kitty, Alacritty (or WSL on Windows)
Screen garbles after resizing Terminal resize event missed Press Ctrl+L, or restart the TUI
Version numbers unchanged after update Old install copy shadowing a new one which opencode (or where on Windows) — confirm which one runs; re-run installer; open fresh terminal
Freezes / keys dead Rare TUI/terminal hiccup Ctrl+C twice to exit cleanly; relaunch. Losing nothing but session view
Everything is slow or erroring at once Provider load/outage today Try a second model/provider (/models); check the provider's status page

Part B: Authentication and keys

Symptom Likely cause Fix
401 Unauthorized / invalid API key Key wrong, revoked, or pasted with a typo Re-run /connect for that provider; paste fresh key; restart OpenCode
/models shows nothing usable No provider configured yet Complete /connect first (Recipe in Ch. 3)
"Model requires a higher plan" (Copilot) That model is tier-gated Pick another model; free plans don't carry top models
Key leaked (committed/pasted anywhere) Rotation needed Revoke at the provider's website → re-/connect → clean the file/commit (Ch. 4)
Auth resets every launch Permissions problem on ~/.local/share/opencode/auth.json Check file exists & is readable by you; re-connect once

Do remember where keys live — ~/.local/share/opencode/auth.json on Linux/macOS/WSL — and that "delete the file" is not the fix for a leak. Revoke-rotate-reconnect is the fix.

Part C: Models and providers

Symptom Likely cause Fix
429 / rate-limit errors Free quota for the hour/day Wait (quota windows reset); switch model/provider; plan offline (Ch. 8)
Tool calls fail or the AI "forgets" instructions mid-task Local model with small context Raise Ollama's num_ctx (16k–32k to start); confirm the model supports tool calls; prefer coder models
Weird refusal-y/beepy answers from a big cloud Wrong provider endpoint or free-tier route swapped to a small model /models, pick explicitly; retry; nothing at all is ever your fault here
Extremely slow responses Server load, or a very big model on weak local hardware Off-peak retry; or check ollama ps — is it CPU-thrashing?
Nonsense answers on a local model Corrupted/partial download, wrong model ollama pull <model> again; check RAM fit for the model size

Part D: Files, edits, and permission prompts

Symptom Likely cause Fix
AI won't read a file .env read is denied by default (by design) Env vars or manual value; true need = explicit override with a reason (Ch. 4)
"Permission denied" prompts flood in "*": "ask" posture That's fine; approve via always for safe categories (git status, grep) once you trust them
AI edits files outside the project external_directory allows it Set explicit path rules; default is ask — keep it
AI repeats the same failing action doom_loop should ask by default Approve investigation or reject; often the underlying task is impossible as stated — re-prompt
AI can't run a specific command Your permission.shell rules deny it Add a precise allow rule (e.g. "pytest *": "allow"), deny for rm * stays

Part E: Project-level oddities

Symptom Likely cause Fix
Every answer misses the project's structure Stale or missing AGENTS.md Re-run /init after big structural changes; commit AGENTS.md (Ch. 2, 6)
AI says the file doesn't exist (it does) Wrong path or context window lost it Use @ to hard-reference it; restart session for a fresh context
Changes lost after closing OpenCode /undo'd but never committed, or plain not-saved Commit early, commit often (Ch. 6) — OpenCode history is not Git history
Everything looks fine but tests fail silently Test command differing from project convention (/init writes the right one) Use the commands in AGENTS.md or ask the AI which test command your project expects

Part F: Git "rescue" recipes

Common beginner Git scares, resolved:

Symptom What is true Fix
"I made a mess and want yesterday's version" Last good commit exists git restore . (unsaved changes) or git checkout <hash> to look back (then branch or copy)
"I staged a secret!" Staging is safe; commit is the door git restore --staged <file> to unstage; if already committed, remove the secret, rotate it at the provider, then commit the removal
"I committed something wrong" Commits are printable history Fix the file, commit again; for fresh local mistakes, git commit --amend is OK. Never rewrite pushed history
"My branch is a disaster" Branchies are free git checkout main (or your main branch), start fresh; delete the ruin with git branch -D <name>

When to ask for help

You are entitled to ask for help, and knowing where helps twice:

  • OpenCode's own docs — opencode.ai/docs — always current, and this book deliberately sticks to their shape.
  • The TUI's /help — the fastest answer for keys and commands.
  • OpenCode's Discord/GitHub — real humans, and bug reports are welcome there. Search first; your exact error text is often already answered.
  • Error messages, verbatim, always travel with you to any of these.

The triage card (when panic arrives)

  1. Fresh terminal. Fresh session.
  2. opencode --version; confirm which binary.
  3. One-variable change; retest.
  4. Read the error verbatim; match it to the tables above.
  5. /models swap to a fallback path.
  6. git status/git diff to confirm nothing precious is lost.
  7. Still stuck: docs → Discord → walk away for ten minutes (seriously, this fixes human-scale bugs).

Ninety percent of beginner "it's broken" moments die by step 4.

Chapter 10 — Appendix: The Checklists and Glossary

This is the shortest chapter and the one you'll use most. It compresses the whole book into routines you can run without re-reading anything. Print these, or keep this chapter open as a tab.

A. First-session setup (once per computer)

  • ☐ Good terminal chosen (WSL on Windows; Ghostty/Kitty/WezTerm elsewhere)
  • ☐ OpenCode installed and opencode --version answers
  • ☐ Git installed and identity configured (git config --global user.name/user.email)
  • ☐ A provider connected via /connect (cloud free tier or local Ollama set up)
  • ☐ /models lists your choice; one chat completed successfully
  • ☐ Basic permission posture set: "*": "ask" for shell, "rm *": "deny", "git push *": "deny" while learning
  • ☐ Keys live in auth.json / env vars — never in project files
  • ☐ Practice folder exists and is far from anything precious

B. Starting a new project

  • ☐ mkdir <project> && cd <project>
  • ☐ git init
  • ☐ .gitignore created (env, secrets, caches — see Chapter 6)
  • ☐ minimal README.md in your own words (three lines counts)
  • ☐ opencode, then /init to generate AGENTS.md; review & personalise it
  • ☐ First commit: git add -A && git commit -m "initial project setup"

C. Every AI work task (the loop card)

  • ☐ git status clean; commit anything pending first
  • ☐ Prompt has all four parts: goal, context (@files), constraints, definition of done
  • ☐ One task per prompt; big tasks went through Plan mode first
  • ☐ AI asked questions (or you asked it: "anything unclear?")
  • ☐ After build: git diff --stat, then read the diff
  • ☐ Review prompts used ("riskiest part? what would you test first?")
  • ☐ Program actually run; old features still fine
  • ☐ No secrets, no weird URLs in the diff
  • ☐ Accept → commit (specific message) — or git restore . and re-prompt

D. Privacy and secrets sweep (every commit — 30 seconds)

  • ☐ git diff --staged shows no keys, tokens, passwords, .env lines
  • ☐ Nothing client/patient/customer-specific in any prompt today
  • ☐ Sensitive work done on a local model, if applicable
  • ☐ No share-links created for private sessions
  • ☐ If a leak happened: revoke → rotate → reconnect → clean the file

E. Free-tier triage (when things get sticky)

  • ☐ Identified the limit: rate quota / context window / quality floor / provider load
  • ☐ Fresh session for a fresh context
  • ☐ AGENTS.md re-/init-ed if structure changed
  • ☐ Rotation considered (/models to secondary cloud or local)
  • ☐ Plan saved on (digital) paper for tomorrow's fresh quota
  • ☐ Provider's current limits page checked within the last 30 days

F. Before telling anyone it "works"

  • ☐ Done-definition met exactly as written in the prompt
  • ☐ Bad inputs tried: empty file, wrong file, no network, giant file
  • ☐ Restarted from scratch once (does it still work?)
  • ☐ Diff reviewed by at least one non-AI intelligence (you)
  • ☐ Committed with a message that explains why
  • ☐ You could explain to a friend what changed without opening the code… going for a second look only

Where to go next

The skills in this book compound in a specific order. Once the loop above feels routine:

  1. Branches and GitHub — publish projects, and let the cloud back up your safety net.
  2. Formatters and tests — automate the parts of review that are mechanical.
  3. Custom agents and MCP servers — teach OpenCode new tools; the same permission thinking gates new power (opencode.ai/docs/agents, /mcp-servers).
  4. Local models, deeper — bigger Qwen/GLM-class models if your hardware allows; the Ollama recipe from Chapter 3 scales up unchanged.
  5. Come back to Chapter 10 — the checklists age well and everything else around them will have changed by then, which is exactly what books are for and pages like this one.

You now know more about working safely and productively with AI coding tools than most people who pay for them. Keep the junior-developer model in mind, keep Git between you and regret, and build something you'd proudly explain to a friend.
